# Правила контраста: что сделано и где крутить

Ветка: **`feat/design-system-page`**, поверх таска 05. Два коммита:

| коммит | что |
|---|---|
| `bd2aab5` | правила контраста: порог по роли текста, полярность плашки, отказ от заливки |
| `6602b43` | правка по итогам разбора корпоративного шаблона MWS: подбор «глубже» сужен |

Change-предложение — `openspec/changes/a-minimum-is-not-a-norm/proposal.md`.
Источник правил — разбор заказчика «Правила контраста. Пример Figma», семь пунктов.

## Что изменилось по сути

Раньше страница **сообщала** о плохом контрасте. Теперь она его **не производит**:
цвет надписи, цвет плашки и решение «заливка или контур» принимает слой, а рендер
только рисует.

Пять правил, которые теперь работают на любом шаблоне:

1. **Порог зависит от роли текста.** Крупный — 3, рабочий — 4,5, подпись и сноска —
   с запасом 7. Крупным считается от 18 pt обычного или 14 pt полужирного.
2. **Минимум — не норма.** Пара, взявшая минимум без запаса, помечается «впритык»
   и не выдаётся за норму.
3. **Полярность раньше контраста.** Тёмная плашка — светлая надпись, светлая — тёмная.
   На средней по яркости плашке тёмная надпись часто берёт больше по формуле
   и читается хуже светлой; такой выбор теперь невозможен.
4. **Плашка уходит глубже, а надпись не чернеет.** Не читается — берётся ближайший
   слот темы той же полярности: тон тот же, светлота другая.
5. **Не держит надпись вовсе — остаётся границей.** Тег и бейдж рисуются контуром,
   а не заливкой с нечитаемой надписью.

Ни одно правило не знает конкретных цветов: всё считается по теме того шаблона,
который пришёл на вход.

## Где крутить

Все пороги — в одном файле, `src/deckforge/designsystem/contrast.py`. Менять только там:
до этого change они были зашиты в трёх местах и разъехались.

| что | где | сейчас | когда менять |
|---|---|---|---|
| порог крупного текста | `MIN_LARGE` | 3,0 | почти никогда: это WCAG |
| порог рабочего текста | `MIN_BODY` | 4,5 | почти никогда: это WCAG |
| **запас для подписи** | `COMFORT_CAPTION` | 7,0 | если решим, что подписи хватает меньшего запаса |
| порог графики и линий | `MIN_GRAPHICS` | 3,0 | если тонкие линии всё равно теряются |
| граница «крупный текст» | `LARGE_PT`, `LARGE_BOLD_PT` | 18 и 14 pt | если в колодах крупным считается другое |
| граница «светлая / тёмная плашка» | `_MID_LUMINANCE` | 0,4 | если на каком-то шаблоне полярность выбрана не так, как видит глаз |
| допуск подбора «тот же цвет глубже» | `PLATE_HUE_DISTANCE` | 90 единиц RGB | если акцент уходит в чужой цвет (было 190 — зелёный уезжал в серый) или, наоборот, слишком часто остаётся контуром |

Логика, а не числа:

* `text_class(size_pt, bold, role)` — какой класс текста у элемента;
* `ink_on_plate(theme, plate, kind)` — надпись на плашке с учётом полярности;
* `deeper_plate(theme, plate, kind)` — тот же цвет глубже плюс надпись к нему;
* `readable_ref` / `readable_from` — слот, берущий порог на этом фоне;
* `best_polar` — лучшее, что даёт тема надписью нужной полярности (им объясняется отказ).

Решение «заливка, глубже или контур» принимается в `synth.py`, функция
`_readable_elements`. Рендер (`export/design_system_page.py`) только читает
`plate_ref`, `shown_ref`, `outlined` и `note` — своей логики цвета у него больше нет.

## Как запустить у себя

```bash
git fetch origin && git checkout feat/design-system-page && git pull
```

Пересобрать страницы по всем шаблонам, что лежат в `tests/fixtures/templates/`:

```bash
python -c "
from pathlib import Path
from deckforge.parsing.template import TemplateParser
from deckforge.designsystem import derive
from deckforge.export.design_system_page import render
out = Path('artifacts/design-system'); out.mkdir(parents=True, exist_ok=True)
p = TemplateParser()
for f in sorted(Path('tests/fixtures/templates').glob('*.pptx')):
    (out / (f.stem + '.html')).write_text(render(derive(p.parse(f, use_cache=False))), encoding='utf-8')
    print(f.stem)
"
```

Или по одному шаблону командой:

```bash
python -m deckforge design-system "tests/fixtures/templates/<файл>.pptx" -o /tmp/ds.html
```

Открыть html двойным кликом. Смотреть разделы **03 — Доступность** (пороги, «впритык»,
места без читаемой пары) и **05 — Плашки и метки** (что стало заливкой, что контуром).

## Как проверить, что правка ничего не сломала

```bash
python -m pytest -q -p no:randomly
python -m ruff check src tests scripts
python -m mypy
python scripts/lint_no_template_constants.py
```

База ветки: **1516 passed, 9 skipped**. Пропуски требуют LibreOffice или модель — это норма.

Тесты правил — `tests/unit/designsystem/test_contrast.py`, шестнадцать штук, каждое
правило на норме и на нарушителе. Если меняешь порог, часть из них покраснеет намеренно:
там зашиты готовые пары серого на белом (4,54 — минимум рабочего текста, 3,03 — крупного,
7,0 — запас подписи). Правь ожидания вместе с порогом, а не вместо него.

Отдельно: `test_no_plate_of_a_case_template_carries_ink_of_the_wrong_polarity` —
главная страховка. Она падает, если на каком-то шаблоне снова появится тёмная надпись
на тёмной плашке. Её ослаблять нельзя.

## Чего не трогать

* `src/deckforge/domain/**` и `schemas/**` — файлы тимлида (правило 11);
* `composition/`, `prompts/`, `audit/`, `rendering/`, `pipeline/`, `export/html.py`,
  `export/pptx.py` — генерация презентаций; этот прогон её не меняет (R18);
* литеральные цвета в коде — запрещены гейтом `lint_no_template_constants.py`.
  Цвет берётся слотом темы, размер — долей величины шаблона.

## Что осталось незакрытым

* **Реальный фон** (пункт 1 разбора): прозрачность плашки, градиент, наложенный эффект
  в манифесте не хранятся. Контраст на подложке-картинке считается по усреднённому цвету,
  и такие пары помечены «приблизительно». Чтобы считать честно, сначала нужно менять
  манифест, а это файлы тимлида.
* **Плашка в композиции** (пункт 6): соседний яркий элемент, текст у края, слишком тонкое
  начертание — это про конкретный слайд, а не про шаблон. Место такой проверки — `audit/`,
  отдельным change.
* Узкие начертания и капитель разбор упоминает, но числом не задаёт; мы их тоже не задаём.
* На корпоративном шаблоне MWS четыре акцента из шести не держат заливку с надписью
  и остаются контуром, а слот `accent1` (очень светлый) не годится под знак на белом —
  это находка по шаблону, а не дефект правил.

## Как отдать правку

Ветка та же, коммит отдельный, тема с номером change:

```bash
git add -A && git commit -m "fix(designsystem): <что поправила>" && git push origin feat/design-system-page
```

PR по ветке уже открыт — коммит попадёт в него сам.
