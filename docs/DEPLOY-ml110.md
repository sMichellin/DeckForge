# DEPLOY-ml110.md — деплой на сервер ml110

Правила общие для тимлида и трёх агентов-исполнителей. Цель та же, что у
[TEAMWORK.md](TEAMWORK.md): чтобы четыре человека работали на одной машине,
не наступая друг другу на ноги и не ломая чужой запуск.

> прогнаны тесты и гейты — §7. Три особенности сервера, которые придётся учитывать

## 1. Доступ: у каждого свой ключ

`ssh -p 43653 -i ~/.ssh/<свой ключ> smichellin@46.32.88.170`

**Общий ключ на четверых не заводим.** Не из вежливости: когда на сервере окажется
сломанный деплой, единственный способ понять, чей он, — журнал подключений. С общим
ключом там будет одно имя на всех.

| Кто | Ключ | Комментарий |
|---|---|---|
| тимлид | `~/.ssh/id_gh_new` | выдан 16.09 |
| поток A | `~/.ssh/id_ml110_a` | запросить у владельца сервера |
| поток B | `~/.ssh/id_ml110_b` | |
| поток C | `~/.ssh/id_ml110_c` | |

Требования к ключу:

* права `600`, иначе ssh откажется его читать;
* **в репозиторий не коммитится никогда** — `.gitignore` не спасёт, если положить
  ключ мимо игнорируемого пути;
* приватный ключ не пересылается в переписке. Публичную часть (`.pub`) — можно.

Удобно завести запись в `~/.ssh/config`, чтобы не повторять флаги:

```
Host ml110
    HostName 46.32.88.170
    Port 43653
    User smichellin
    IdentityFile ~/.ssh/id_ml110_b     # свой
    IdentitiesOnly yes
    ServerAliveInterval 30
```

Дальше везде просто `ssh ml110`.

## 2. tmux обязателен

Любая операция дольше минуты — только внутри tmux. Деплой роняет ssh-сессию регулярно:
рвётся Wi-Fi, засыпает ноутбук, обрывается VPN. Без tmux сборка образа умирает на
середине и оставляет после себя половину слоёв и заблокированный каталог хранилища.

```bash
ssh ml110
tmux new -As deckforge-b          # своя сессия, имя = свой поток
# ... работа ...
# Ctrl+B, затем D — отцепиться, процесс продолжает работать
```

Вернуться: `ssh ml110 -t 'tmux attach -t deckforge-b'`.

**Имя сессии — по своему потоку**: `deckforge-lead`, `deckforge-a`, `deckforge-b`,
`deckforge-c`. Чужую сессию не трогать: `tmux attach` к чужой работе покажет её,
а `tmux kill-session` уничтожит.

Посмотреть, кто чем занят: `tmux ls`.

## 3. Что деплоим и откуда

**Только из git, только из `main`.** Правок прямо на сервере не делаем: они не
воспроизводятся, теряются при следующем `git pull` и не видны в ревью.

```bash
ssh ml110 -t 'tmux new -As deckforge-b'

# первый раз
git clone git@github.com:sMichellin/slide_write_gen_vid.git ~/deckforge
cd ~/deckforge/code/deckforge

# дальше
git fetch origin && git reset --hard origin/main
```

Если нужно проверить **свою ветку** до мержа — это отдельный каталог, а не переключение
в общем:

```bash
git clone --branch feat/<change-id> ... ~/deckforge-b-<change-id>
```

Так чужой прогон не сломается оттого, что кто-то переключил ветку под ним.

## 4. Сборка и запуск

Локально на сервере тоже **ничего не устанавливаем** — правило 9 из
[AGENTS.md](../AGENTS.md) действует и здесь. Всё через podman:

```bash
make image          # образ приложения
make worker-image   # образ воркера: приложение + LibreOffice, внутри гейт кириллицы
make test           # тесты
make gates          # лицензии C1/C2 и константы шаблона C6
```

### Запуск сервисов: venv на время работы

`podman compose` на этом сервере не работает без провайдера (§8.2), а ставить его
в систему нельзя — машина общая. Поэтому `podman-compose` живёт во временном venv
**ровно на время работы с контейнерами** и удаляется следом:

```bash
cd ~/deckforge-src
python3 -m venv venv && source venv/bin/activate && pip install podman-compose

make up             # API, воркер, UI, Redis, LanguageTool
make logs
make down

deactivate && rm -rf venv
```

**Удалять venv обязательно, а не «когда-нибудь».** Причин две. Диск общий и почти
полный (§8.3), а каталог venv занимает под сотню мегабайт. И `venv/` в рабочем дереве
репозитория — это лишний каталог, который рано или поздно попадёт в `git status`
и чью-то команду `git add -A`.

Сборка образов и прогон тестов в venv **не нуждаются**: они идут через `podman build`
и `podman run` напрямую.

### Порты: у каждого свои

Compose по умолчанию занимает 8080 (API), 8501 (UI), 6379, 9000/9001, 8010. Четыре
одновременных запуска подерутся за них, и проигравший молча не поднимется.

| Кто | Смещение портов | API | UI |
|---|---|---|---|
| тимлид | +0 | 8080 | 8501 |
| поток A | +10 | 8090 | 8511 |
| поток B | +20 | 8100 | 8521 |
| поток C | +30 | 8110 | 8531 |

Задаётся переменной окружения перед `make up`:

```bash
export DECKFORGE_PORT_OFFSET=20
```

Если переменная не поддержана в `docker/compose.yaml` на момент чтения — это задача
тимлида, запросите (TEAMWORK.md §4: `docker/**` его файл).

## 4а. Стенд: прогон вне процесса API (28.09)

Стенд поднимается пятью скриптами из `~/e2e-work/stand/`, а не `make up`: на сервере
`podman compose` требует провайдера, и ради него ставить в систему ничего нельзя (§8.2).

```bash
bash ~/e2e-work/stand/redis.sh          # очередь arq
bash ~/e2e-work/stand/languagetool.sh   # орфография полного аудита
bash ~/e2e-work/stand/api.sh            # API :8080, очередь arq
bash ~/e2e-work/stand/worker.sh         # прогон вне процесса API
bash ~/e2e-work/stand/ui.sh             # интерфейс :8501
```

**Почему не `InlineQueue`.** До 28.09 стенд держал прогон задачей в цикле событий API
(`~/e2e-work/inline_app.py`). Цена была такая: блокирующие стадии (разбор `.pptx`,
`soffice`, вызовы llama.cpp) замораживали цикл на минуты, опрос статуса ждал, интерфейс
отдавал человеку `httpx.ReadTimeout` вместо статуса, а перезапуск API убивал идущие
прогоны. На профиле `final` — три варианта и судья-VLM — это гарантировано.

С воркером цикл API свободен: замер на идущем прогоне (`3e31bf35b614`, профиль `demo`)
— статус отвечает за **7–8 мс**, пока прогон идёт. Перезапуск API прогонов больше
не убивает; убивает перезапуск **воркера** — задача живёт в нём.

Прежний режим остался флагом: `QUEUE=inline bash ~/e2e-work/stand/api.sh`.

**Профиль прогона** задаётся переменной: `PROFILE=demo bash ~/e2e-work/stand/ui-run-content.sh`
(она уезжает в поле `profile` запроса `POST /runs`). Из интерфейса профиль выбирается
выпадашкой — API его принимает и проверяет по `available_profiles()`.

Что проверить после подъёма:

```bash
curl -s localhost:8080/profiles          # {"profiles":["demo","dev","final"]}
podman logs --tail 3 deckforge-worker    # «Starting worker for 2 functions»
podman ps                                # пять контейнеров: api, worker, ui, redis, languagetool
```

## 5. Секреты на сервере

`.env` создаётся **на сервере руками**, из `.env.example`, и в git не уезжает:

```bash
cp .env.example .env
$EDITOR .env        # вписать ключи провайдеров
chmod 600 .env
```

Ключи инференса у каждого свои — квота общая на токен, и чужой прогон легко съест её
целиком. Какие провайдеры пригодны и где брать ключи — [inference-providers.md](inference-providers.md).

## 6. После деплоя: что проверить

Деплой считается состоявшимся, только если всё это отвечает:

- [ ] шаблоны кейса разобраны в кэш (см. ниже) — иначе первый прогон на незнакомом
      шаблоне встанет в очередь к VLM;
- [ ] `make test` зелёный **на сервере**, а не только локально;
- [ ] `make gates` проходит;
- [ ] `podman ps` показывает поднятые сервисы, ни один не в состоянии `Restarting`;
- [ ] API отвечает: `curl -sf localhost:$((8080+OFFSET))/docs >/dev/null && echo ok`;
- [ ] гейт кириллицы в образе воркера прошёл при сборке (иначе сборка бы упала).

Если что-то не поднялось — `make logs` и разбор, а не повторный `make up`.

### Предразбор шаблонов (D1)

Разметку макетов делает VLM через общий однослотовый сервер, и очередь к нему ничем
не ограничена: прогон `aa5eca9aa135` разбирал незнакомый шаблон **2375 с** при бюджете
стадии 25 с (§12). В прогоне это теперь ограничено пределом времени
(`DECKFORGE_LAYOUT_VLM_BUDGET_S`, по умолчанию 25 с) с откатом на эвристику — но откат
размен качества на время, и разменивать его на известных шаблонах незачем.

```bash
make warm-cache TEMPLATES="tests/fixtures/templates/*.pptx"
```

Скрипт разбирает шаблоны **без предела времени** и кладёт манифесты в тот же кэш,
из которого их возьмёт прогон (`$DECKFORGE_ARTIFACTS_DIR/template-cache`). Дальше разбор
известного шаблона стоит чтения json.

Гонять заново нужно **после каждой правки парсера**: кэш инвалидируется сменой
`PARSER_VERSION`, и устаревший манифест прогон честно разберёт сам — то есть снова
встанет в очередь.

### Откат

```bash
git reset --hard <предыдущий коммит main>
make image && make up
```

Образы предыдущих сборок остаются в хранилище podman, поэтому откат быстрый.
Раз в неделю чистить: `podman image prune -f`.

## 8. Особенности этого сервера

### 8.1 Системный `registries.conf` сломан

`/etc/containers/registries.conf` содержит опечатку: `insecure = truey` вместо `true`
в записи локального реестра `192.168.1.250:5000`. Любой `podman build` падает:

```
Error: loading registries configuration: toml: line 29: expected value but found "truey"
```

Файл принадлежит root и правится другим проектом, поэтому чиним **у себя**, а не там:

```bash
mkdir -p ~/.config/containers
printf 'unqualified-search-registries = ["docker.io"]
' > ~/.config/containers/registries.conf
```

Для rootless podman пользовательский конфиг главнее системного. Один раз на каждого.

### 8.2 `podman compose` не работает — нет провайдера

`podman compose version` → `looking up compose provider failed`. Ни `podman-compose`,
ни `docker-compose` не установлены, поэтому **`make up` на этом сервере не поднимется**.

Собрать образ и прогнать тесты это не мешает — всё через `podman run`. Для сервисов
нужен `podman-compose`; ставить его на чужую машину без спроса не стоит, запросите
у владельца сервера.

### 8.3 Диск: 7,5 ГБ свободно, и он общий

После нашей сборки занято 92 %. На машине лежит 8,5 ГБ образов **другого проекта**
(`robozon-vision`, `robozon-gz`).

**`podman image prune -a` на этой машине запускать нельзя** — снесёт чужую работу.
Чистить только за собой и по имени:

```bash
podman image rm localhost/deckforge:dev
```

Образ воркера с LibreOffice (+2,5 ГБ) на таком остатке собирать рискованно. Нужен он —
сначала освободите место или согласуйте с владельцем.

### 8.4 Репозиторий приватный, у сервера нет доступа к GitHub

`ssh -T git@github.com` → `Host key verification failed`, ключа с доступом к репозиторию
на сервере нет. Пока не заведён deploy key, код возится git-бандлом:

```bash
# на своей машине
git bundle create /tmp/deckforge-main.bundle main
scp -P 43653 -i ~/.ssh/<свой ключ> /tmp/deckforge-main.bundle smichellin@46.32.88.170:/tmp/

# на сервере
git clone -b main /tmp/deckforge-main.bundle ~/deckforge-src
```

Бандл — полноценный git-репозиторий с историей, поэтому правило «деплоим только из git»
соблюдается: на сервере видно, какой именно коммит развёрнут.

**Правильное решение — deploy key**: сгенерировать на сервере ключ, добавить публичную
часть в настройки репозитория (Settings → Deploy keys, read-only). Тогда обычный
`git fetch && git reset --hard origin/main` из §3 заработает как написано.
