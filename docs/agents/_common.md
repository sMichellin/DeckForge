шаблона (кейс «Цифровой дизайнер презентаций», ЛЦТ 2026). Репозиторий:
`/Users/mvorotyagin/ml_projects/2026/slide_write_gen_vid/code/deckforge`.

Ты один из трёх агентов, работающих параллельно. Тимлид сливает ваши ветки.

## Прочитать перед началом, в этом порядке

1. `docs/TEAMWORK.md` — правила параллельной работы: владение файлами, ветки, мерж.
   **Это главный документ, нарушение его правил ломает работу двух других агентов.**
2. `AGENTS.md` — нерушимые правила проекта и что значит «не зашито под шаблон».
3. `ARCHITECTURE.md` §1–§6 — ограничения ТЗ, ADR, границы слоёв, контракты.
4. `IMPLEMENTATION.md` — свой раздел («Поток A/B/C») и статус соседей.

## Как всё запускается

Локально **ничего не устанавливается**. Только podman:

```bash
export PATH="/opt/podman/bin:$PATH"
make image      # собрать образ приложения
make test       # тесты
make lint       # ruff
make typecheck  # mypy strict
make gates      # гейты ТЗ: лицензии моделей (C1/C2) и константы шаблона (C6)
```

Для рендера превью нужен образ с LibreOffice: `make worker-image`, тесты — `make preview-test`.

Для живого инференса профили в `docs/inference-providers.md`; ключи в `.env` (в git не идёт).
Бесплатно и по правилам ТЗ работает Groq и локальный Ollama; у HuggingFace и OpenRouter
квоты выработаны.

## Пять правил, нарушение которых заметят на защите

1. **Никаких констант конкретного шаблона.** Ни RGB, ни имён гарнитур, ни размеров в EMU,
   ни имён макетов. Всё из `TemplateManifest`. Проверяется `make gates`.
   Система должна знать *способ получить ответ* для любого шаблона, а не ответ для одного.
2. **Слой не импортирует слой выше себя.** Порядок: domain → registry → inference →
   parsing → planning → layout → composition → rendering → audit → export → pipeline → api.
   Проверяется `tests/unit/test_architecture_boundaries.py`.
3. **LLM не пишет .pptx и не пишет код вёрстки** — только валидируемый `SlideIR` (ADR-001).
4. **Промпты только в `prompts/`**, загрузка через `deckforge.registry`. В коде их нет.
5. **`src/deckforge/domain/**` заморожен.** Нужно поле — запрос тимлиду, см. TEAMWORK.md §4.
   Не добавляй сам: сломаешь две чужие ветки и все golden-схемы.

## Порядок работы

Спек-первым, цикл OpenSpec: `explore → propose → apply → verify`.

1. `git fetch origin && git switch -c feat/<change-id> origin/main`
2. Изучить задачу и существующий код. **Прогнать на настоящем шаблоне, если change
   касается разбора или вёрстки** — шаблоны не в git, положи свои в
   `tests/fixtures/templates/` (каталог в `.gitignore`).
3. `openspec/changes/<change-id>/proposal.md`: что выяснилось при разведке, что предлагается,
   чем проверяется. Разведка — не формальность: на этом проекте живые прогоны уже трижды
   опровергали допущения, записанные в архитектуре.
4. Реализация с тестами.
5. `git rebase origin/main`, PR в `main`, CI зелёный.

## Definition of Done — в `docs/TEAMWORK.md` §6

Отдельно: **всё, что не заработало, не измерено или отложено, пишется в proposal.md**
в раздел «Что осталось незакрытым». Тимлид решает, что дескоупить, но только если знает
о проблеме. Незаявленная дыра всплывёт на защите, и это худший момент для сюрприза.

Не жди молча и не обходи препятствие времянкой. Таблица ситуаций — `docs/TEAMWORK.md` §8.
