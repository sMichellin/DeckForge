# Задания потокам — дизайн-система в генерации, а не только на странице

22.09 влит PR #142: из любого шаблона собирается страница его дизайн-системы
(`deckforge design-system <шаблон>`), появился слой `designsystem`. Это **шаг 3**
из четырёх, которые просила заказчица. Её постановка дословно:

> получает шаблон — делает анализ — составляет дизайн систему — **верстает слайды
> по дизайн системе**

Шаг 4 не сделан, и шага 1–2 (ДС как этап конвейера) тоже нет. В манифесте прогона
эти требования стоят со статусом `deferred`:

| ID | Требование | Где живёт сейчас |
|---|---|---|
| R23 | «агент просто кладёт текст на слайд» — вёрстка слайдов по ДС | только `.autopilot/2026-09-22-design-system-page--wip/manifest.md` |
| R24 | ДС как этап конвейера, а не отдельная команда | там же |

**Почему это надо вынести в план.** Слой `designsystem` импортируют ровно два места:
`cli.py` и `export/design_system_page.py`. В `pipeline`, `composition`, `layout`,
`rendering`, `planning` и `audit` — ни одного упоминания. На собранную колоду страница
не влияет никак: кейс оценивает презентации, а дизайн-система пока рядом с ними.

## Что уже разошлось в две стороны

Пока у ДС один потребитель — страница, расхождение безвредно. С шагом R23 на один
и тот же вопрос будет два ответа.

| Вопрос | Ответ ДС | Ответ генерации |
|---|---|---|
| Какой контраст достаточен | `designsystem/contrast.py`: классы текста, 4,5 / 3,0, комфорт 7,0 для подписи, 3,0 для графики | `configs/audit_checks.yaml`: `min_ratio` 4,5, `min_ratio_large` 3,0, `large_text_pt` 18 |
| Какой цвет читаем на заливке | `contrast.readable_ref`, `ink_on_plate`, `deeper_plate` | `domain.rules.readable_text_ref` (зовёт `rendering/writer.py`) |
| Каким кеглем набрано число | `DesignSystem.number_sizes` из KPI-компонента шаблона | своё правило вёрстки KPI (регрессия B13, #139) |
| Каковы пропорции компонента | `DesignSystem.components` | `manifest.components` напрямую (DS4) |

## Задачи

Порядок продиктован зависимостями: DG1 убирает двоемыслие до того, как им начнут
пользоваться; DG2 даёт ДС конвейеру; DG3 — единственная задача, меняющая вид колоды;
DG4 нужен раньше DG3, иначе часть дизайн-системы нарисовать нечем.

```
DG1 (C) ─┐
DG2 (тимлид) ─┴─ DG4 (тимлид) ─ DG3 (A+B)
```

### DG1. Один свод правил о контрасте — поток C

`audit.template.contrast_below_wcag` и `rendering/writer.py` переходят на
`designsystem.contrast`; пороги остаются параметрами проверки в
`configs/audit_checks.yaml`, но берутся по классу текста, а не один на всю колоду.
Change: `one-contrast-rule`.

Мерить: находки `template.contrast_below_wcag` по чекпойнтам последних прогонов
на трёх шаблонах до и после. Расхождения объяснить поимённо — новых ложных быть
не должно. Тесты на нарушителе и на норме по правилу 7.

### DG2. Дизайн-система — этап конвейера (R24) — тимлид

`derive(manifest)` считается один раз в узле `parse_template` и кладётся в состояние
графа рядом с манифестом. Ни модели, ни сети, ни файлов: стоимость — доли секунды,
бюджет §12 не трогается. Страница и CLI продолжают работать как раньше.
Change: `design-system-in-the-pipeline`.

Мерить: время стадии `parse_template` до и после на трёх шаблонах — прирост ≤ 1 с;
`run.json` получает `design_system` в сводке прогона.

### DG3. Вёрстка по дизайн-системе (R23) — потоки A и B

Композиция и вёрстка перестают решать сами то, на что ДС уже ответила: роль цвета
блока, кегль числа, пропорции и отступы компонента, маркер списка. Поток A — выбор
роли и запрос компонента, поток B — раскладка по шкале отступов ДС.
Change: `compose-by-the-design-system`.

Мерить прежними мерилами, три прогона с разными сидами: `run_metrics.py`
(визуализаций, заголовков подрезано, ошибок аудита) и C9 (доля слайдов с пустой
зоной ≥ 40 % ширины). Ухудшения ни по одному числу быть не должно.

### DG4. IR умеет то, что показывает страница — тимлид

Страница достраивает callout «инсайт» и «риск», цитату с акцентной полосой,
разделители и пагинацию. В IR восемь видов блоков: текст, список, диаграмма, таблица,
схема, иконка, картинка, KPI — этих нет. Нужен маленький PR тимлида с новыми видами
блоков до DG3, иначе половина достроенного останется только на картинке.
Change: `ir-callout-and-quote`. Правит `domain/**` и `schemas/**` (правило 11).

Мерить: `make schemas` без расхождений, рендер каждого нового блока на трёх шаблонах,
холодный шаблон по правилу 10.

## Что осталось незакрытым в самом прогоне #142

Не задачи потоков, а хвосты, которые видит только автопилот:

* папка прогона помечена `--wip`, а в `.autopilot/state.js` общая фаза «manifest —
  active», таск 04 в ревью, таск 05 в работе. PR влит целиком — дашборд показывает
  неправду;
* последний пункт самого PR — посмотреть четыре собранные страницы глазами — не сделан;
* 13 мелких замечаний исполнителя лежат в `state.js`, поле `concerns`. Два самых
  похожих на ошибку поведения проверены при ревью и подтвердились как хрупкость,
  а не как дефект: `STEP_SOURCE` покрывает все четыре значения `base_source`,
  списки акцентов в `measure` и `synth` расходятся намеренно;
* CI по PR не отработал ни разу: конфликт в `.gitignore` не давал GitHub собрать
  merge-коммит, а на `push` в `main` рабочий процесс не настроен. Единственная
  проверка этого кода — локальный прогон при ревью: 1585 тестов, `ruff`, `mypy`
  и гейт C6 чисто.
