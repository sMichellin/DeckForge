наполнение конкретного макета. Вёрстка, рендер и аудит — не твои, ими заняты агенты B и C.

## Задачи по порядку

### (7) `content-ingestion` — начинай с неё

`parsing/content.py`. markitdown → нормализованный markdown → факты, датасеты, ассеты.

`extract_numbers()` работает по-русски и на реальных формах записи: «37,5 %»,
«1 200 млн ₽», «x2.3», «в 2,5 раза», «−12 п.п.». Сохраняй исходное написание в `Number.raw`:
на нём держится фактчекинг, который будет сверять число со слайда с исходником.

**Критерий выхода:** каждое число из контента получило `fact_id`. Без этого проверке
`content.numbers_grounded` из аудита не на что опереться, и агент C не сможет её закрыть.

### (10) `deck-planning`

`planning/planner.py`, `planning/narrative.py`. Промпт `deck_planner@1.0.0` готов —
читай его, он уже задаёт требования.

Один вызов LLM на всю колоду (бюджет 35 с, §12). В промпт уходят **доступные виды
макетов манифеста**, а не сам шаблон: планировщик не должен знать, что внутри файла.

**Критерий выхода:** `DeckPlan` на 12 слайдов, где заголовок — вывод, а не тема.
«Выручка» — плохо, «Выручка выросла на 37 % за год» — хорошо. Требование закладывается
в промпт, а не чинится авто-фиксом после: чинить поздно, когда план уже построен.

### (11) `slide-composition` + (20) `layout-variants`

`composition/{composer,layout_picker,visual_selector}.py`. Промпт `slide_composer@1.0.0` готов.

Подбор макета — из манифеста, по виду и вместимости, никогда по имени. При нехватке
места деградация на более простой макет **того же шаблона** (§15).

Три варианта вёрстки — это три прохода с разными `VariantProfile` из `configs/variants.yaml`,
а не три ветки кода (ADR-005). Файл конфига уже написан и обоснован, реализация за тобой.

Выбор типа диаграммы: сначала детерминированные правила
(`domain.rules.choose_chart_type` уже реализован), LLM — только на пограничных случаях.

**Критерий выхода:** `SlideIR` проходит валидацию схемы; макет всегда из манифеста;
три варианта визуально различимы и все проходят аудит соответствия шаблону.

## Что уже есть и чем пользоваться

| Нужно | Где | Готово |
|---|---|---|
| Клиент LLM, guided decoding по JSON Schema, ретраи, кэш | `deckforge.inference` (`client_for`, `generate_model`) | change 8 |
| Загрузка промптов по версии | `deckforge.registry.get_prompt_registry()` | change 9 |
| Манифест шаблона: тема, типошкала, сетка, макеты, вместимость | `deckforge.parsing.TemplateParser` | changes 3–6 |
| Профили вариантов | `deckforge.registry.load_variant_profiles()` | готово |

`generate_model()` сам чинит невалидный ответ, возвращая модели текст ошибки валидации,
и сдвигает seed на повторе. Не пиши свой цикл ретраев.

## Чего опасаться

**Модели размышляют.** Qwen3.x отдают размышление отдельно, и `content` пуст, пока бюджет
токенов не позволит дойти до ответа. Клиент это уже умеет, но бюджет `max_tokens` ставь
с запасом: для плана колоды 4096 мало не покажется.

**Схема гарантирует форму, но не смысл.** `layout_id`, которого нет в манифесте, формально
валиден. Проверяй такие вещи сам после валидации.

**Квоты кончаются.** Если провайдер отдал 402, клиент поднимет `InferenceQuotaError` —
не глуши его, переключай профиль и отмечай в proposal.
