# TEAMWORK.md — параллельная работа трёх агентов

Правила существуют ради одного: чтобы три ветки слились в одну **без потери качества**
и без ручного разруливания конфликтов. Всё остальное — следствие.

Роли: три агента-исполнителя (A, B, C) и тимлид, который мержит и владеет контрактами.

---

## 3. Ветки и PR

```
main ← feat/<change-id>        одна ветка на один change, без вложенности
```

1. Перед началом: `git fetch origin && git switch -c feat/<change-id> origin/main`.
2. Перед PR: `git rebase origin/main`. **Merge-коммитов в ветку не делать** — история
   должна оставаться линейной, иначе разбирать три параллельных ветки станет больно.
3. PR — в `main`, всегда. Стопки PR друг на друге не строим: они дают ложные диффы
   и ломаются, когда нижний мержат.
4. CI зелёный — условие ревью, а не его результат. Красный PR не смотрят.
5. Один change = одна ветка = один PR. Если change разросся, разбить на два, а не
   тащить всё в один.

Если `git rebase` дал конфликт в **чужом** файле — остановиться и сообщить тимлиду.
Конфликт в чужом файле означает, что границы владения нарушены, и разруливать его
в своей ветке — значит прятать проблему.

## 4. Контракты заморожены

`src/deckforge/domain/**` и сгенерированные из него `schemas/**` меняет **только тимлид**.

Причина простая: доменные модели — единственный способ передачи данных между слоями
(ARCHITECTURE.md §4). Если три агента правят их параллельно, ломаются все три ветки
разом, а golden-схемы дают конфликт в каждом PR.

**Нужно новое поле или enum — не добавляйте его сами.** Опишите тимлиду:

* какое поле, какого типа, в какой модели;
* что без него нельзя сделать;
* кто ещё им будет пользоваться.

Тимлид вносит изменение в `main` отдельным маленьким PR, прогоняет `make schemas`
и сообщает всем троим, что пора делать `rebase`. Это занимает минуты и стоит дешевле,
чем разбор трёх конфликтующих версий контракта.

Так же — с зависимостями: `poetry add` делает тимлид (правило 8 из AGENTS.md).

## 5. Как править IMPLEMENTATION.md

У каждого агента свой раздел: «Поток A», «Поток B», «Поток C».
Правьте **только свой**. Статус меняется в том же PR, что и код, — change без
обновлённого статуса считается незакрытым.

Шапку файла, таблицу артефактов сдачи и раздел тимлида не трогать.

## 6. Definition of Done

PR не считается готовым, пока не выполнено всё:

- [ ] `make test` зелёный, `make lint` и `make typecheck` чистые
- [ ] `make gates` проходит (лицензии C1/C2 и константы шаблона C6)
- [ ] у каждого нового поведения есть тест; у проверки аудита — **два**: на нарушителе и на норме
- [ ] прогон на настоящем шаблоне, если change касается парсера, композитора или рендера
- [ ] `openspec/changes/<id>/proposal.md` заполнен по факту: что выяснилось, что решено, что осталось незакрытым
- [ ] статус в своём разделе `IMPLEMENTATION.md` обновлён
- [ ] ветка перебазирована на свежий `origin/main`, CI зелёный
- [ ] чужих файлов в диффе нет

**Отдельно про честность отчёта.** Если что-то не заработало, не измерено или отложено —
это пишется в `proposal.md` в раздел «Что осталось незакрытым». Тимлид принимает решение
о дескоупе, но только если знает о проблеме. Незаявленная дыра всплывёт на защите.

## 7. Мерж: порядок и ответственность

Мержит **тимлид**. Порядок — по слоям снизу вверх, потому что нижние слои у верхних
в зависимостях:

```
A (parsing/content, planning, composition)
  → B (layout, rendering, export)
    → C (audit, api, ui)
      → тимлид: (17) pipeline-orchestration и сборка end-to-end
```

Это не очередь ожидания: все трое работают одновременно с первого дня. Порядок касается
только мержа готовых PR. Готовый раньше срока PR мержится раньше — при условии, что он
не ждёт чужого кода.

После каждого мержа тимлид пишет остальным: «`main` обновлён, сделайте rebase».
Rebase на свежий `main` — обязанность автора ветки, не тимлида.

Change (17) `pipeline-orchestration` делает тимлид **после** A, B и C: граф связывает
все слои, и писать его параллельно с ними значит переписывать на каждый мерж.

## 8. Деплой на ml110

Правила — [DEPLOY-ml110.md](DEPLOY-ml110.md). Коротко, чтобы не читать целиком:

* у каждого **свой ssh-ключ**, общий на четверых не заводим: иначе по журналу не понять,
  чей деплой сломался;
* всё дольше минуты — **внутри tmux**, сессия названа по своему потоку
  (`deckforge-a/b/c/lead`). Чужую сессию не трогать;
* деплоим **только из `main`**, правок прямо на сервере не делаем;
* у каждого **своё смещение портов**, иначе четыре запуска подерутся за 8080 и 8501;
* `.env` создаётся на сервере руками и в git не уезжает;
* `podman-compose` ставится во **временный venv** на время работы с контейнерами
  и удаляется следом (`deactivate && rm -rf venv`): машина общая, диск почти полон.

## 9. Что делать, когда заблокирован

Не ждать молча и не обходить препятствие «пока что времянкой».

| Ситуация | Что делать |
|---|---|
| Нужно поле в `domain` | запрос тимлиду (§4), пока — работать над другой частью своего change |
| Нужен чужой код, которого ещё нет | написать против интерфейса и покрыть тестами на подделке, как сделано с `VlmClient` в change (5) |
| Конфликт в чужом файле | остановиться, сообщить тимлиду |
| Требование ТЗ противоречит архитектуре | `/opsx:explore`, предложение с обоснованием, а не правка на ходу |
| Кончилась квота провайдера | переключиться на другой профиль (`docs/inference-providers.md`), отметить в proposal |

Подделка вместо недостающего кода — нормальный приём, но только за узким интерфейсом
и с тестами. Времянка внутри чужого слоя — нет.
