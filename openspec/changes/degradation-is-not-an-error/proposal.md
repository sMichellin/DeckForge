# degradation-is-not-an-error

Правка к change (23) `service-api`. Capability: `service-api`. Поток C.
Задание C.2 из [docs/agents/tasks-after-ui-run.md](../../../docs/agents/tasks-after-ui-run.md).

Статус: proposed → applied

## Explore

`api/jobs.py:133` складывал два разных списка в одно поле:

```python
trouble = [*report["errors"], *report["degradations"]]
... error="; ".join(trouble) or None
```

У прогона `b8549ea89984` состояние было `done`, ошибок ноль, а в `error` стоял текст
«audit: смысловой аудит выключен — остатка бюджета не хватает (§15)». Интерфейс рисует
`status["error"]` через `st.warning`, и удачный прогон выглядел как прогон с бедой.

Это не косметика. Деградация — **выбор пайплайна**: §15 разрешает выключить дорогую
стадию, чтобы уложиться в бюджет; колода при этом собрана и годна. Ошибка — что-то
не отработало. Пока они в одном поле, ни человек, ни клиент API отличить их не могут,
а «оно всегда что-то пишет в error» кончается тем, что поле перестают читать —
вместе с настоящими ошибками.

## Propose

1. **`RunStore.write_status` принимает `degradations`** и пишет их отдельным полем
   `status.json`. Статус по-прежнему переписывается целиком.
2. **`_finish` кладёт в `error` только `report["errors"]`**, деградации — в своё поле.
3. **`RunStatus` (DTO) получает `degradations: list[str]`** — клиенту API они видны
   без чтения отчёта.
4. **Интерфейс**: деградации показываются `st.info`, а не `st.warning`, и остаются
   в одном месте — в сводке отчёта. Дублировать их в статусе не стали.

### Требования

**Требование: у удачного прогона поле ошибки пусто.** Прогон в состоянии `done`
без ошибок SHALL иметь `error == null`.

- **WHEN** прогон дошёл до конца с деградацией по бюджету
- **THEN** `state = "done"`, `error = null`, деградация в `degradations`
- **WHEN** прогон дошёл до конца, но часть работы не отработала
- **THEN** текст в `error`, как и прежде

## Verify

Три новых теста в `tests/unit/test_api_service.py`: деградация не попадает в `error`
у успешного прогона, настоящая ошибка попадает, поле доезжает до клиента через `GET /runs/{id}`.

Полный прогон: `1005 passed, 3 failed, 28 skipped` — те же три падения, что на `origin/main`
(`language_tool_python` не установлен). ruff и mypy strict чисты.

## Что осталось незакрытым

1. **`frontend/` не покрыт ни ruff, ни mypy** — в `Makefile` они гоняются по
   `src tests scripts`, а `[tool.mypy] packages = ["deckforge"]`. Просьба к тимлиду
   прежняя (см. раздел `web-ui` в IMPLEMENTATION.md); правка `frontend/app.py`
   здесь проверена ruff вручную.
2. **Долги C.3 не тронуты** и остаются открытыми: падение UI с `RemoteProtocolError`
   при перезапуске API, прогон-сирота в `running` после перезапуска `InlineQueue`,
   `load_run_config()` без профиля в `api/jobs.py`. Это отдельный change, и смешивать
   его с этим PR не стали.
3. **Живьём не видели.** Нужен прогон через UI на ml110.
