# markitdown-extras

Правка зависимостей по запросу потока A из change (7). Тимлид (`pyproject.toml` — §2).

Статус: proposed → applied

## Explore

Поток A в proposal change (7) заявил дыру уровня продукта, а не своей зоны:

> В образе нет конвертеров markitdown — `.docx` и `.pdf` не читаются вообще. ТЗ
> предполагает контент-пакет заказчика, и сейчас сервис прочтёт из него только
> markdown и txt.

Проверено, и оказалось шире заявленного:

```
markitdown  есть      (базовая сборка)
mammoth     НЕТ       → .docx не читается
pdfminer    НЕТ       → .pdf не читается
openpyxl    НЕТ       → .xlsx не читается, хотя код его импортирует
```

`markitdown = "^0.1"` ставит базовую сборку: у пакета конвертеры вынесены в extras
(`docx`, `pdf`, `xlsx`, `pptx`, `xls`, …). Без них `MarkItDown` поднимается и честно
отказывается на каждом бинарном формате.

`openpyxl` — отдельная история: `parsing/content.py` импортирует его напрямую (датасеты
читаются из `.xlsx` в обход markitdown, потому что тот отдаёт «2025.0» и «NaN» как
значения), но в зависимостях его не было. Приезжал транзитивно и мог исчезнуть при любой
пересборке — то есть `.xlsx` ломался бы молча и не на той машине, где это заметили бы.

Последствие для ТЗ: из контент-пакета заказчика сервис взял бы только `.md` и `.txt`.
Все три формата, которые реально присылают (Word, Excel, PDF), не читались.

## Propose

```toml
markitdown = { version = "^0.1", extras = ["docx", "pdf", "xlsx", "pptx"] }
openpyxl   = "^3.1"
```

`pptx` в extras — не про наш рендер: это чтение **входящих** презентаций, если заказчик
пришлёт материалы слайдами. `xls` (старый формат) не включён: не встречался, а тянет
лишнюю зависимость.

## Что осталось незакрытым

Настоящего контент-пакета от организаторов по-прежнему нет — вся разработка на
синтетическом (п. 2 и 3 «незакрытого» у потока A остаются в силе). Сканированные PDF
не поддерживаются: OCR в зависимости не тянем.
