# run-profile-from-api

Правка change (23) `service-api` и `web-ui`. Задание C1 из
[tasks-20-09.md](../../../docs/agents/tasks-20-09.md).

Статус: proposed → applied

## Explore

`api/jobs.py:95` звал `load_run_config()` без аргумента. Профили лежат рядом и готовы
(`configs/profiles/{dev,demo,final}.yaml`), но через сервис до них было не дотянуться:
CLI умеет `--config`, а у прогона из интерфейса такого рычага нет вовсе.

Цена — не в удобстве. Смысловой аудит включается ровно строкой `audit.run_semantic: true`,
и она есть только в `demo` и `final`. Значит любой прогон через UI шёл без него, и проверить
смысловой аудит живьём было нельзя в принципе — при том, что механика готова с change (18).

Вторая находка по дороге: `load_run_config` несуществующий профиль **молча пропускает** —
`if profile_path.exists()`. Опечатка в имени дала бы базовый конфиг и ни слова об этом.
Человек узнал бы через 150 секунд по отсутствию смысловых находок в отчёте, если бы
вообще заметил.

## Propose

Профиль едет в `RunRequest` и оттуда в `load_run_config`. Три решения по дороге:

**Имя профиля проверяет маршрут, а не DTO.** `POST /runs` с неизвестным профилем
отвечает 400 и перечисляет существующие. Ловить опечатку через две с половиной минуты
прогона — то же самое, что не ловить. В `schemas.py` этой проверки нет намеренно: DTO
транспорта не ходит на диск.

**Список профилей отдаёт сервис** (`GET /profiles`), а не хранит интерфейс. Профиль —
это файл (C11), и знать их наперечёт не должен никто: положили
`configs/profiles/<имя>.yaml` — он появился в выпадашке.

**Отказ сервиса не роняет боковую панель.** `client.profiles()` при любой ошибке отдаёт
пустой список. В этой же панели живёт поле с адресом сервиса, и если бы недоступность
долетала до разметки, человек, ошибившийся адресом, не смог бы его исправить: страница
падала бы раньше, чем покажет поле. Пустой ответ не кэшируется — поправил адрес,
и на следующей перерисовке список приедет.

Молчание остаётся молчанием: без профиля прогон идёт по `default.yaml`, как и раньше.

### Чего здесь сознательно нет

`Settings.profile` (`DECKFORGE_PROFILE`, по умолчанию `dev`) в коде не используется
нигде. Соблазн подставить его как запасной вариант был, но это сменило бы поведение
всех прогонов на стенде разом: сегодня они идут по базе, а стали бы по `dev` — шесть
слайдов вместо двенадцати и `llm_fast` вместо `llm_main`. Отдельный разговор, не этот PR.

`target_slides` и `variants` из профиля на прогон через API не влияют: число слайдов
пайплайн берёт из `brief` (`plan.py:154`), вариант — из `request.variant`. Это не сломано,
а так и задумано — «один прогон — один вариант вёрстки» (`RunRequest`). А вот `exports`
профиль задаёт: с `demo` HTML не соберётся, и кнопка выдачи останется пустой. Интерфейс
это переживает — «не готово» он уже отличает от ошибки.

## Verify

Девять тестов. Сервис: список профилей приходит с диска; запрошенный профиль попадает
в `request.json`; молчание остаётся `None`; неизвестное имя — 400 с перечнем; профиль
доезжает до `load_run_config`, и `demo` включает `run_semantic`. Интерфейс: список
спрашивается у сервиса; мёртвый сервис и мусор вместо ответа дают пустой список, а не
исключение; «по умолчанию» уезжает как `None`, а не как имя профиля.

Набор целиком: 1158 passed, 19 skipped. Четыре падения в `main` — `language_tool_python`
не установлен локально, `test_audit_runner`, `Metropolis.pptx` — были до правки и к ней
не относятся. Гейты C1/C2 и C6 зелёные, `ruff check` чист.

**Живьём не проверено.** Нужен прогон на ml110 с профилем `demo`: смысловой аудит
на однослотовом сервере — 36 минут (C2), в бюджет 300 с он не войдёт. То есть выбрать
профиль теперь можно, а дождаться результата — пока нет; это задание C2, отдельное.
