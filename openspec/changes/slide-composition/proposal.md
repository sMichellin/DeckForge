# slide-composition

Changes (11) и (20) из ARCHITECTURE.md §14. Capabilities: `slide-composition`,
`layout-variants`. Поток A.

Статус: proposed → applied

## Explore

### 1. Всё, на что опирается композиция, уже написано соседями

`domain.rules.choose_chart_type` (тимлид), `layout.fit_slide` (поток B, change 12),
`rendering.writer` (поток B, change 13), промпт `slide_composer@1.0.0` и
`configs/variants.yaml`. Работа зоны — связать это, а не написать заново.

### 2. Вид макета обещает возможность, но не гарантирует её

Классификатор определяет вид по геометрии, и макет может быть назван диаграммным,
не имея плейсхолдера под диаграмму. Если доверять только виду, на слайде окажется
пустая рамка. Поэтому выбор проверяется по `LayoutCapacity`: `supports_chart`,
`supports_table`, `supports_image`, `max_chars_body`.

### 3. Предпочтение варианта нельзя применять как фильтр

`variants.yaml` объявляет `layout_preference`, например у варианта B — `kpi, chart,
image_full`. Шаблон на защите будет незнакомым, и таких видов в нём может не быть вовсе.
Фильтр оставил бы вариант B без единого макета.

### 4. `capacity_ratio` высокой плотности выше предела ТЗ по заполненности

`Density.HIGH` даёт 0.92, Приложение 1 ТЗ считает нарушением заполненность выше 0.75.
Прямого конфликта нет: `capacity_ratio` — доля **вместимости плейсхолдера**, а проверка
ТЗ — доля **площади слайда**, и плейсхолдеры занимают не весь слайд. Расхождение
зафиксировано тестом, чтобы оно оставалось осознанным.

## Propose

### Соответствие роли слайда и вида макета

Утверждено владельцем потока A. Цепочка от предпочтительного к запасному:

| Роль | Цепочка видов |
|---|---|
| `title` | title |
| `section` | section → title |
| `agenda`, `problem`, `solution` | bullets → two_column |
| `evidence` | chart → table → bullets |
| `metrics` | kpi → chart → table → bullets |
| `comparison` | two_column → table → bullets |
| `process` | two_column → bullets |
| `roadmap` | table → two_column → bullets |
| `summary` | bullets → kpi → two_column |
| `closing` | closing → title → section |

Предпочтение варианта — **приоритет, а не фильтр**: оно переставляет виды внутри цепочки
роли и может добавить свой, но только если слайду есть чем его наполнить (`image_full`
не предлагается слайду без картинки, `chart` — слайду без данных). Титул, раздел и финал
предпочтениям не подчиняются: титул обязан быть титулом в любом варианте.

Крайний случай — ни один вид не нашёлся: берётся любой макет шаблона с местом под текст.
Отказ здесь хуже деградации: колода из одиннадцати слайдов вместо двенадцати — это
невыполненное задание, а простой макет того же шаблона фирменный стиль не нарушает.

### Рычаг деградации

Решение владельца потока A: содержимое всегда умещается на один слайд, слайд не делится.
Различается **что приносится в жертву**:

| Условие | Жертвуем | Сохраняем |
|---|---|---|
| автор просил сохранить формулировки | визуализацию (диаграмма → таблица → буллеты) | текст дословно |
| по умолчанию | текст сокращается | визуализацию |

Обоснование: тип визуализации выбран под данные детерминированным правилом, это
осмысленное решение; формулировку же можно ужать без потери смысла.

### Выбор типа диаграммы — правилом, а не моделью

`domain.rules.choose_chart_type` плюс детерминированное распознавание временного ряда
(кварталы, годы, месяцы, даты; порог 75 % подписей, потому что рядом с кварталами
в выгрузках попадается «Итого»). Тип навязывается модели и переписывается в ответе,
если та его поменяла: иначе три варианта начнут различаться случайно, а не по объявленной
оси (C7, C11).

### Привязка ответа к реальности

Схема гарантирует форму, но не осмысленность. После валидации: макет ставится тот,
что выбрало правило; блоки с чужими `placeholder_idx` выбрасываются; висячие ссылки
на датасеты и ассеты снимаются; буллеты режутся до шести (Приложение 1 ТЗ); слайд,
от которого не осталось блоков, — ошибка, а не пустая страница.

## Проверка

* макет всегда из манифеста и никогда не по имени;
* титул не подчиняется предпочтению варианта;
* отсутствующий вид деградирует внутри того же шаблона;
* предпочтение варианта работает приоритетом: цепочка роли из него не исчезает;
* вариант не добавляет вид, который слайду нечем наполнить;
* **три варианта выбирают разные макеты для одного и того же слайда** (C7) —
  на шаблоне с богатым набором видов, потому что на бедном они честно совпадут;
* плотности трёх вариантов различны;
* обе ветки рычага деградации доезжают до промпта.

## Запросы тимлиду

**`Brief.preserve_wording: bool = False`** — рычаг деградации сейчас работает параметром
композитора со значением по умолчанию, потому что в контракте поля нет. Нужно: решение
принимает автор презентации, а значит место ему в брифе. Пользоваться будет композиция;
аудит сможет объяснять, почему текст сокращён.

## Что осталось незакрытым

1. **Живого прогона не было** — по той же причине, что и в change (10): облачный провайдер
   недоступен из рабочего окружения, локальная модель не укладывается в бюджет ТЗ.
2. **Различимость вариантов доказана на уровне выбора макета, но не на рендере.**
   Требование ТЗ — «визуально различимы»; увидеть это можно только на картинках,
   а значит после сборки колод потоком B.
3. **SmartArt и иконки** — change (21), кандидат на дескоуп.
4. **Сокращение текста выполняет слой `layout`** (поток B, стратегия `shorten`):
   композиция только инструктирует модель и режет число буллетов.
