# schema-patterns-per-provider

Правка к change (8) и уточнение вчерашнего решения #44. Capability: `inference`.

Статус: proposed → applied

## Explore

Сквозной прогон на ml110 падал на стадии `plan`:

```
400 Failed to initialize samplers: failed to parse grammar
```

Вывод, сделанный по этому сообщению в #44, был слишком широким: «llama.cpp не осиливает
схему `DeckPlan`», и structured output выключили целиком. Последствие оказалось хуже
исходной болезни — **без схемы модель возвращает свою структуру**:

```json
{"deck": {"title": "…", "slides": [{"role": "…", "layout": "…", "title": "…", "body": "…"}]}}
```

Цикл починки переспрашивал трижды по 70 секунд, и прогон умирал по таймауту через 18 минут.

Проверка вариантов схемы на живом сервере расставила всё по местам:

| Вариант схемы `DeckPlan` | Грамматика |
|---|---|
| как есть (strict) | **400** |
| **без `pattern`** | **собирается** |
| доменная, без strict | 400 |
| доменная, без strict и без `pattern` | собирается |
| тривиальный объект | собирается |

Ломает не схема и не её размер, а **два поля с `pattern`**: `SlidePlan.slide_id`
(`^s\d{2,}$`) и `DeckPlan.variant` (`^[A-Z]$`). llama.cpp переводит JSON Schema в GBNF
и регулярное выражение такого вида не переваривает.

## Propose

**`pattern` — ограничение на значение, а не на форму ответа.** Его в любом случае
проверяет Pydantic на нашей стороне. Поэтому провайдеру, который на нём спотыкается,
схема отправляется без `pattern`, а не не отправляется вовсе: отдать форму без одного
ограничения лучше, чем не отдать формы.

`ModelSpec.supports_schema_patterns` (по умолчанию `true`) объявляет это свойство
бэкенда; `InferenceClient` вырезает `pattern` перед отправкой, когда флаг снят.

**Свойство принадлежит бэкенду, а не роли.** В `configs/models.local.yaml` флаг снят
и у `llm_fast`, и у `vlm_judge`: они смотрят на один сервер. Схема судьи из двух полей
`pattern` не содержит и работала (141 вызов в замере стабильности), но объявить честно
дешевле, чем искать причину заново на первой же проверке с `pattern`.

**`supports_structured_output` возвращён в `true`.** Решение #44 отменяется: выключать
guided decoding не нужно, достаточно не слать одно поле.

### Требования

**Требование: неподдерживаемое ограничение не отменяет схему целиком.** Клиент SHALL
отправлять схему без `pattern` провайдеру, объявившему `supports_schema_patterns: false`.

- **WHEN** схема содержит `pattern` на любой глубине, а провайдер их не компилирует
- **THEN** запрос уходит со схемой без `pattern`
- **AND** форма ответа по-прежнему задана, а `pattern` проверяется доменной моделью

## Verify

971 passed, 17 skipped; ruff, mypy strict и гейт C6 чисты. Два теста: вырезание `pattern`
на любой глубине с сохранением формы и значение флага по умолчанию.

## Что осталось незакрытым

1. **Живой прогон плана с этой правкой ещё не сделан.** Грамматика собирается — это
   измерено; что модель со схемой вернёт валидный `DeckPlan`, покажет только прогон.
   Это следующий шаг.
2. **Промпт планировщика форму по-прежнему не диктует** — задача потока A
   (`docs/agents/tasks-after-live-run.md`). Схема её задаёт, но у провайдеров без
   structured output опорой остаётся только промпт.
3. **Флаг проверяется руками, а не автоматически.** Узнать, что новый бэкенд не варит
   `pattern`, можно лишь получив 400. Предполётная проверка схемы при старте была бы
   надёжнее — отдельная правка.
