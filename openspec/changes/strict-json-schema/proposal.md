# strict-json-schema

Правка change (8) `inference-client`. Тимлид (`inference/**` — §2).

Статус: proposed → applied (частично; см. «незакрытое»)

## Explore

Обнаружено при первом **живом** прогоне потока A (PR #25). До этого structured output
проверялся только схемами, написанными руками, — и они случайно удовлетворяли
требованиям строгого режима.

Схема, выведенная из доменной модели, отвергается **до модели**:

```
400 invalid JSON schema for response_format: 'DeckPlan':
    /$defs/SlidePlan/required: `required` is required to be supplied and to be an array
    including every key in properties
```

Pydantic помечает обязательными только поля без значения по умолчанию. Строгий режим
требует перечислить в `required` **все** свойства. Поэтому structured output с доменными
моделями не работал против строгих провайдеров (Groq, OpenAI) ни разу — просто никто
не пробовал вживую.

Отказ от строгого режима не помогает: с `strict: false` Groq схему **принимает,
но игнорирует** — модель вернула `{"/": {"widget_NAME": "text", ...}}`, ничего общего
с `SlideIR`.

## Propose

`strict_schema()` приводит любую схему к строгому виду прямо перед отправкой запроса —
так покрыты оба пути: схема из доменной модели и готовая из
`prompts/<скилл>/<версия>/schema.json`.

Что делается:

* все свойства переносятся в `required`, необязательным разрешается `null`;
* `X | None`, где `X` — перечисление, сворачивается в одно поле с `null` в `enum`:
  строгий режим не умеет различать ветви `anyOf` из ссылки и `null`;
* на каждый объект ставится `additionalProperties: false`;
* голые `$ref` внутри `oneOf`/`anyOf` встраиваются: ссылку внутри ветви строгий режим
  не разворачивает и требует `additionalProperties` на самой ветви.

## Verify

Проверено на живом Groq: `DeckPlan` проходит, **планирование заработало** —
8 слайдов за 27 с при бюджете 35 с, заголовки получились выводами:

```
s02 [problem ] LLM не пишет код вёрстки и файлы .pptx
s03 [solution] Маршрут: LLM создаёт JSON-IR, рендерер собирает файл
s05 [comparison] JSON-IR надёжнее кодогенерации и конвертации HTML в pptx
```

773 теста зелёные, ruff и mypy чисты.

## Что осталось незакрытым

**`SlideIR` строгий режим Groq выразить не может в принципе.** Упирается в
`dict[str, X]`: провайдер требует `additionalProperties: false` на каждом объекте,
а это прямо противоречит словарю с открытым набором ключей. В нашем IR так описаны
`SlideIR.fit_report` и `ChartBlock.axis_titles`.

Приведением схемы это не лечится. Лечится сужением: **схема ответа скилла должна
описывать только то, что модель действительно производит.** `fit_report` считает слой
`layout` по метрикам гарнитуры, единицы осей берутся из датасета — модель не должна
заполнять ни то, ни другое, и в схему они попали лишь потому, что
`scripts/gen_schemas.py` выводит её из доменной модели целиком.

Проверено на живом Groq: после удаления `fit_report` и `provenance` из схемы ошибка
уходит именно на них и всплывает следующая, на `axis_titles` — то есть диагноз верен.

Это задача потока A (`prompts/slide_composer/**`) вместе с правкой генератора схем
(`scripts/gen_schemas.py`, тимлид). Оформлена отдельно.

**Проверка на llama.cpp не сделана** — свой сервер не отвечал в момент прогона
(третий раз за сессию). Он использует GBNF-грамматики и к схемам терпимее; возможно,
`SlideIR` пройдёт там без сужения. Это не отменяет задачу: полагаться на единственную
личную машину нельзя, а на Groq и OpenAI ограничение останется.
