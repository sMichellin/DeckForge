# audit-run-params

Правка к change (17). Запрос потока C из #28. Capability: `pipeline-orchestration`, `audit-semantic`.

Статус: proposed → applied

## Explore

`configs/default.yaml` и профили объявляют пороги аудита, судья читает их из `ctx.params`,
а в `ctx.params` приезжают только `params` из `configs/audit_checks.yaml`. Между этими
двумя местами не было ни одного пути: значение в профиле лежало мёртвым.

Последствие крупнее, чем «ключ не читается»:

| Профиль | Объявлено | Работало |
|---|---|---|
| `demo` (запись видео, A4) | `vlm_votes: 1` | 3 |
| `final` (сдача, A3/A11) | `vlm_votes: 3` | 3 — совпало случайно |

Смысл профиля `demo` — предсказуемое время на записи. Одно голосование вместо трёх это
**втрое меньше вызовов VLM**; по замеру change (18) — 84 вызова на чистой колоде вместо 252.
Профиль просил, аудит не слышал, и заметили бы это по секундомеру на записи.

## Propose

Пороги прогона едут в проверку **под** её собственными:

```python
params = {**self.run_params, **spec.params}
```

Порядок именно такой, а не наоборот. `spec.params` — калибровка конкретной проверки
(change «audit-calibration», #26), она измерена на 59 слайдах и профилем молча
переопределяться не должна. `run_params` закрывают другой случай: параметр, которого
у проверки в YAML нет вовсе (`vlm_votes` у судьи), — без этого пути он не доедет никак.

**Рычаг графа и порог проверки — разные вещи.** `run_semantic`, `run_deterministic`,
`auto_fix`, `max_fix_rounds` решают, что делает граф, и в `ctx.params` им делать нечего.
Узел `audit` отсекает их по списку и передаёт остальное. Список — отрицательный,
а не положительный: имена порогов принадлежат проверкам, и граф их знать не должен.

Тест `test_every_pipeline_key_of_the_default_config_is_known` падает на новом ключе
в `audit:` — чтобы рычаг не уехал в пороги молча, а порог не остался мёртвым.

### Требования

**Требование: порог профиля доезжает до проверки.** Прогон аудита SHALL передавать
проверке пороги из `audit:` профиля запуска, кроме ключей, управляющих графом.

- **WHEN** профиль объявляет `audit.vlm_votes: 1`
- **THEN** судья получает `ctx.params["vlm_votes"] == 1`
- **AND** порог, объявленный у проверки в `configs/audit_checks.yaml`, не меняется

## Apply

`audit/runner.py` — необязательный `run_params` (правка в файле потока C, см. ниже);
`pipeline/nodes/audit.py` — `check_params()` и передача; `tests/unit/test_audit_run_params.py`.

## Что осталось незакрытым

1. **Правка в файле потока C.** `audit/runner.py` принадлежит C (TEAMWORK.md §2), и я его
   тронул: без точки входа в `AuditRunner` профильные пороги не доставить никак — контекст
   собирается внутри прогона. Правка аддитивная (необязательный аргумент, поведение
   по умолчанию не меняется), открытых веток у C нет, конфликта быть не должно. C предупреждён.
2. **На живой модели не проверено.** Что `vlm_votes: 1` действительно втрое сокращает
   вызовы, показывает счётчик `VlmJudge.calls` на живом прогоне — вместе с замером
   стабильности вердиктов (18) на ml110.
3. **`vlm_confidence_threshold` проверен только транзитом.** Значение доезжает тем же путём,
   но его влияние на вердикт меряется опять же живой моделью.
